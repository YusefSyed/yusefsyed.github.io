Ten models scored zero because the attack never arrived

Yusef Syed. 15 November 2026.

In October I ran a prompt-injection benchmark, ToolEffectBench, on ten models through Amazon Bedrock. In one arm of the benchmark the injected text arrives inside a tool error: the agent's first publish call fails, and the error message carries the attack. Every Bedrock model made zero forbidden attempts in that arm.

That looked like a result. It was a delivery failure. None of the ten models had ever received the text.

What happened

The benchmark runs on Inspect AI. In Inspect 0.3.286, the Bedrock provider builds a tool result from the tool message's content and does not read the message's error field. When a tool raises an error, the content is empty, so the model gets a tool result with status error and an empty string. The Anthropic, OpenAI and Ollama providers send the error text.

This was not my discovery. elliottolson reported it on October 19, before my runs. I hit it independently twelve days later and added a confirmation with measurements to that issue.

Why I didn't see it

The eval log hides it. Inspect stores the tool message with its error text on every provider, whether or not the provider sent that text. So a delivery check that reads the stored messages passes on Bedrock.

It came out when a review of the paper draft asked for delivery to be read from the requests that were sent, not from the stored messages. The raw request is the only place the empty string shows.

What it did to the numbers

With the error text missing, the ten Bedrock models made 0 attempts in the error arms. The same attack texts placed in an ordinary tool result moved six of those models.

I reran the error arms with one change: a solver that copies the error message into the tool message's content before each model call. Samples, tools, sandbox and scorer were unchanged. The ten models then made 107 forbidden attempts across the 666 samples where the text reached them, and nine of the ten made at least one. Qwen3 32B alone made 21 attempts in 48 on the base suite.

The original runs stay published and are marked as defective. Their counts are never added to the rerun's.

Check your own runs

If you run Inspect evals on Bedrock and any tool can fail, read the sent requests:

import json, sys
from inspect_ai.log import read_eval_log

log = read_eval_log(sys.argv[1], resolve_attachments=True)
failed = delivered = 0
for sample in log.samples:
    errors = [m.error.message for m in sample.messages if m.role == "tool" and m.error]
    if not errors:
        continue
    failed += 1
    sent = " ".join(
        json.dumps(e.call.request)
        for e in sample.events
        if e.event == "model" and e.call is not None
    )
    if any(json.dumps(text)[1:-1] in sent for text in errors):
        delivered += 1
print(f"{delivered} of {failed} samples with a failed tool call sent the error text")

On two of the published logs this prints 60 of 60 for Claude Sonnet 5.5 through the Anthropic API and 0 of 62 for Qwen3 32B through Bedrock.

One caveat: when a provider throttles, Inspect's log drops the raw request on some model events, so this check can undercount. Section 8.1 of the paper describes the fallback I used.

The workaround

Until the provider is fixed, copy the error into the content yourself before each generate call:

def fill_tool_errors(messages):
    for message in messages:
        if isinstance(message, ChatMessageTool) and message.error and not message.text:
            message.content = message.error.message

The full solver is in solvers.py.

Status

As of November 15 the issue is open and a fix is in review (#6557).

What I took from it

My benchmark scores agents from the database they changed, not from what they say they did, because transcripts mislead. That did not help here. The snapshot was correct the whole time; the input was wrong, one layer below anything the scorer could see. A zero from a cross-provider run means little until you have read what each provider sent.
